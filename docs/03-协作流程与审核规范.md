# DH2 协作流程与审核规范

本文档定义 架构师 Agent / 开发 Agent / 用户 三方的工作循环。**这是所有迭代的法定流程。**

## 1. 迭代生命周期

```
┌─────────┐   迭代任务包(任务书+技术设计+测试设计)   ┌─────────┐
│ 架构师    │ ───────────────────────────────────▶ │ 开发Agent │
│ (规划/审核)│                                     │ (编码/测试)│
└─────────┘ ◀─────────────────────────────────── └─────────┘
     ▲        交付物(代码+测试+实施自检报告)            │
     │                                             │
   审核门禁(第4节)                                   │
     │ 通过 ▶ 架构师发放下一轮迭代任务包                │
     │ 不通过 ▶ 整改清单,开发Agent返工                 │
     │                                             ▼
     └──────── 用户:真机验证项执行并回填报告 ◀──────────┘
```

每个迭代固定五步:

1. **发包**:架构师在 `docs/iterations/{迭代号}/` 写齐三份文档:`ITER-*-任务书.md`(范围+交付物+验收标准)、`ITER-*-技术设计.md`(实施细则)、`ITER-*-测试设计.md`(测试用例)。
2. **实施**:开发 Agent 按文档编码、写测试、执行 `dotnet build` + `dotnet test`,填写 `ITER-*-实施自检报告.md`(模板见第 3 节)。
3. **审核**:架构师按第 4 节门禁逐项审查,输出 `ITER-*-审核报告.md`,结论为 `APPROVED` 或 `CHANGES_REQUIRED(附整改项)`。
4. **真机验证**:涉及游戏环境的验收项由用户执行,回填任务书中的真机验证报告模板。
5. **闭环**:全部通过后,架构师发包下一迭代。

**迭代内执行方式:按 Sprint 阶段推进**(细则见 [07-Scrum开发流程](07-Scrum开发流程.md),Story 卡在各迭代 `sprints/` 目录):开发 Agent 一次只实施当前 Sprint,完成即停;架构师 Sprint Review(轻量四项门禁)通过后才发放下一 Sprint;**禁止一次性从头到尾连续开发**。

## 2. 角色契约

| 角色 | 必须做 | 禁止做 |
|---|---|---|
| 架构师 | 维护 docs/01~06;编写迭代任务包;逐项审核;维护迭代状态表 | 直接编写实现代码(审核发现的微小笔误除外,须在审核报告中声明) |
| 开发 Agent | 按技术设计实现;测试先行;跑通 build+test;写自检报告;提交约定式 commit | 修改 docs/01~06 与迭代任务书;偏离技术设计时不声明;触碰红线 API(01 文档第 3 节) |
| 用户 | 执行真机验证并回填报告;做封号风险等决策 | — |

**技术设计偏离规则**:开发 Agent 认为设计有问题时,不得擅自改架构,应在自检报告"变更说明"中提出,由架构师在审核中裁决;确需改动的,架构师先修订技术设计文档再允许实施。

## 3. 交付物契约与自检报告模板

每个迭代交付:

1. 源代码(符合 04 编码规范,build 零警告零错误);
2. 测试代码(按该迭代测试设计,全部通过);
3. `docs/iterations/{迭代号}/ITER-*-实施自检报告.md`,模板:

```markdown
# ITER-{X} 实施自检报告
- 开发Agent / 日期 / commit hash:
- 环境(.NET SDK 版本 / OS):

## 验收标准自查
| AC | 结果 | 证据(文件/日志/命令输出路径) |
|----|------|------------------------------|
| AC-01 | 通过/未通过 | ... |

## build & test 结果
(粘贴 dotnet build / dotnet test 摘要)

## 相对技术设计的偏离与理由
(无 / 逐条列出)

## 遗留问题与风险
```

## 4. 审核门禁(逐项检查,全部通过才可 APPROVED)

| # | 门禁 | 检查方式 |
|---|---|---|
| G1 | **红线扫描**:代码中不出现禁止 API | 全仓 grep:`ReadProcessMemory\|WriteProcessMemory\|VirtualAllocEx\|CreateRemoteThread\|SetWindowsHookEx\|OpenProcess`(含 P/Invoke 声明与 NuGet 引入);检查 csproj 无注入/钩子类包 |
| G2 | **架构符合性**:项目/依赖方向与 02 文档第 3 节一致 | 审阅项目引用图 |
| G3 | **编码规范**:符合 04 文档 | 抽查 + `dotnet format --verify-no-changes` |
| G4 | **测试门禁**:`dotnet test` 全绿;核心逻辑覆盖率 ≥ 70% | 亲自复跑 |
| G5 | **可复现**:干净目录 clone 后 build+test 成功 | 实际执行 |
| G6 | **验收核对**:任务书 AC 逐条核对证据 | 对照自检报告与实物 |
| G7 | **文档同步**:README/配置样例/模板 manifest 与实现一致 | 审阅 |

## 5. 审核报告格式

```markdown
# ITER-{X} 审核报告
- 审核人:架构师Agent / 日期
- 结论:APPROVED | CHANGES_REQUIRED

## 门禁结果
| 门禁 | 结果 | 说明 |
|------|------|------|

## 整改项(仅 CHANGES_REQUIRED 时)
| # | 级别(阻塞/建议) | 位置 | 问题 | 要求 |
|----|------------------|------|------|------|
```

整改项全部关闭并复验后,才允许 APPROVED 与发包下一轮。

## 6. 真机验证协议

- 真机验证项在任务书中以 `[真机]` 标注,并附**操作步骤 + 证据要求(截图/日志路径)+ 报告模板**;
- 用户回填后,架构师将结论纳入审核依据;
- 真机结论可能改变技术路线(如 M0 后台消息验证失败 → 全局切焦点轮转),此时架构师负责修订 02 文档相关章节并重发受影响迭代的设计。

## 7. Git 规范

- **远端仓库:`https://github.com/DreamALittle/DahuaOnlineSupport.git`**(用户创建;`docs/` 文档基线由架构师维护并推送至 `main`);
- **开发 Agent 接到任务包后的第一步:`git clone` 该仓库**到自己的工作区,核对 `docs/` 基线与对应迭代任务包齐全,然后创建 `iter/{迭代号}` 分支开始开发;
- 分支:`main` 保护(仅审核通过后合入);开发分支 `iter/{迭代号}`,如 `iter/m0`;
- 提交信息:约定式(`feat: ...` / `test: ...` / `docs: ...` / `refactor: ...`);
- 每迭代至少一个 merge commit 到 main,附审核结论摘要;
- `artifacts/`(报告输出)、`bin/`、`obj/`、`data/*.db` 进 .gitignore。
