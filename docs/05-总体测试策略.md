# DH2 总体测试策略

## 1. 四层测试体系

| 层 | 名称 | 依赖 | 运行环境 | 目的 |
|----|------|------|----------|------|
| L1 | 单元测试 | 无外部依赖 | CI/本地 | 纯逻辑:FSM 转移、配置解析、坐标换算、manifest、阈值判定、金样本截图识别 |
| L2 | 模拟窗口测试 | DH2.MockGame | 本地桌面 | 感知+行为+任务引擎端到端:真实截屏、真实 PostMessage、真实识别 |
| L3 | 回放测试 | 录制的截图序列 | CI/本地 | 真机截图序列回放,验证场景分类与 FSM 演进(无需游戏在跑) |
| L4 | 真机验证 | 真实游戏 | 用户机器 | 最终验收,按任务书 `[真机]` 项执行并回填报告 |

**核心原则:开发 Agent 在无游戏环境下必须能完成 L1~L3 全部编码与执行;L4 由用户执行。**

## 2. DH2.MockGame 模拟窗体(贯穿全项目的测试基础设施)

Avalonia 应用,模拟游戏的关键 UI 形态与消息行为:

- **M0(v0)**:固定 800×600;左上任务追踪栏(深色底白字);一个"前往"按钮;点击后状态机 idle→寻路中→已到达→(点"返回")→idle,计数+1;以 `SetWindowSubclass`(同进程子类化自身窗口,非全局钩子)记录原始鼠标消息,另以 Avalonia Pointer 事件记录语义点击,双路写入同一日志文件。
- **M1(v1)**:增加可切换场景(对话/战斗/弹窗/掉线)、任务追踪栏文本 OCR 用例、师门全流程模拟(NPC、交付)。
- **M2+ (v2)**:多实例五开模拟、随机弹窗注入、模拟掉线窗口。

MockGame 的界面布局常量写入 `configs/mock-layout.yaml`,既是测试断言依据,也是模板生成的基准。

## 3. 金样本库(golden samples)

- `tests/golden/screenshots/`:按 `{场景}/{序号}.png` 组织的真机/模拟截图;
- `tests/golden/expectations/`:与截图对应的期望场景/期望识别结果 JSON;
- 游戏改版或识别误判案例,必须先沉淀金样本再修模板(防回归)。

## 4. 各层职责与门禁

| 层 | 覆盖对象 | 通过标准 |
|----|----------|----------|
| L1 | Core/Vision(静态图)/Tasks(注入事件)/Guardian 决策 | 全绿,核心项目行覆盖 ≥70% |
| L2 | 截屏→识别→决策→输入 全链路(对 MockGame) | 关键用例全绿;e2e 冒烟必须自动化 |
| L3 | 感知层对真机序列的分类正确率 | 100%(已沉淀样本不允许分类回退) |
| L4 | 任务书 AC 的 `[真机]` 项 | 用户回填报告 |

## 5. 测试数据管理

- 涉及账号信息的测试数据一律用占位符(`mock_actor_1`),禁止真实角色名入仓;
- 录制回放数据(截图序列)按需入仓,单序列 ≤ 50 帧,超出裁剪关键帧。

## 6. 性能与稳定性测试

- 感知循环性能:单 Actor 1 FPS 常态下单帧处理耗时 ≤ 200ms(截屏+全订阅 ROI 识别,普通 4 核 CPU);
- 五开压力:5 Actor 并行 1 FPS,CPU 总占用 ≤ 50%;
- 稳定性冒烟:MockGame 上连续运行师门模板 20 轮无人工干预、无未处理异常。
